# 代码质量检查流程:文档 + 最小自动化落地

目标:把现在「全靠手动自觉」的质量防线变成「一条命令 + 一个 CI 门禁 + 一页文档」。不做 pre-commit 钩子、不引格式化工具(保持改动面最小)。

## 1. 补齐工具链(package.json + 2 个新配置文件)

- `npm i -D eslint eslint-config-next @eslint/eslintrc`
- 新建 `eslint.config.mjs`:flat config,extends `next/core-web-vitals` + `next/typescript`,ignores 加 `.next/`、`open-next/` 等
- package.json scripts 调整:
  - `lint`:`eslint .`(Next 16 已移除 `next lint` 命令,现 script 双重坏死:命令没了 + eslint 没装)
  - 新增 `typecheck`:`tsc --noEmit`
  - 新增 `check`:`typecheck && lint && test`(一条命令跑「三绿」中的静态两绿 + 单测)
- **首遍 lint 分诊**:全量跑一遍,真问题低成本修掉;噪音规则降为 warn 或在 config 关闭,不为过 lint 大改业务代码

## 2. CI 质量门禁(新文件 `.github/workflows/ci.yml`)

- 触发:push 到 main + pull_request
- 步骤:checkout → setup-node 22(cache: npm)→ `npm ci` → `typecheck` → `lint` → `test` → `npm run build`
- env 全用占位值,照抄 cf-deploy.yml 的模式(stripe 占位字符串 + `DATABASE_URL` 占位连接串——经验库 infra-gotchas #5:构建期模块顶层求值需要它)
- 落地前先在本地用同样占位 env 验证 `next build` 能过,再提交 workflow
- 不动现有两个部署 workflow

## 3. 流程成文(根目录 `QUALITY-CHECKLIST.md`,与 DEPLOY-CHECKLIST.md 呼应)

五层检查,内容来自经验库已沉淀的惯例:
1. **改动中**:改面向用户文案 → 同步 grep `messages/zh.json`/`en.json` 双语对账
2. **提交前**:跑 `npm run check`(typecheck + lint + vitest);金钱路径改动加跑 pricing/submit 双向一致性测试
3. **推送前**:较大改动过 `/code-review`(Standards + Spec 两轴)
4. **UI/文案改动**:真实浏览器 GUI 回归矩阵(亮暗 × 中英 × 桌面/移动)——静态全绿也省不掉
5. **部署前**:按 `DEPLOY-CHECKLIST.md` 冒烟顺序 + 部署后 48h 观察

`AGENTS.md` 加一行:代码质量检查以 `QUALITY-CHECKLIST.md` 为准,提交前跑 `npm run check`。

## 4. 验收

- 本地 `npm run check` 全绿 + 占位 env 下 `npm run build` 成功
- CI 门禁在 push 后自动生效(是否 commit/push 由你决定;push 后 CI 会真正跑起来)

## 5. 经验沉淀(AGENTS.md 硬性要求)

按 magiviz-playbook 沉淀模式,把「Next 16 lint 从零接入(移除 next lint 后的正确姿势)+ push 触发质量门禁」写回 `references/methods.md` / `infra-gotchas.md` 后再收尾。
